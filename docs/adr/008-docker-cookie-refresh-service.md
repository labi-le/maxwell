# 2026-10-26 - Docker cookie refresh service

- Решение: бот синхронно вызывает sidecar `cookie-refresh` по HTTP при явной ошибке авторизации, истёкших cookies или недоступном jar, без завершённых файлов. Sidecar опрашивает `pc` и `notebook` по SSH, запускает на них `export_chrome_cookies.py`, выбирает самый свежий профиль Chrome с cookie нужного источника и атомарно заменяет общий `cookies.txt` с правами `0600`. Бот повторяет загрузку ровно один раз. Ответ сервиса кэшируется на 5 секунд, чтобы видео и фото X в одной загрузке не запускали повторный экспорт.
- Почему: Chrome на ноутбуке и ПК содержит актуальные сессии, а ключ расшифровки находится в keyring соответствующего хоста. Старый путь через Firefox, SQLite-запросы и таймер на рабочем ПК оставлял бота в ожидании до 60 секунд и требовал ручного восстановления. Синхронный вызов убирает фоновый таймер и не даёт контейнеру бота доступ к SSH-ключу.
- Отвергнуто: экспорт Firefox, постоянный доступ контейнера к профилю браузера, слияние профилей `pc` и `notebook`, обновление от любой HTTP 403, повтор завершённой загрузки, публикация порта сервиса, передача cookie values в лог или ответ и прямая запись во временный файл `yt-dlp`. Эти варианты смешивают аккаунты, создают ложные повторы или раскрывают секреты.
- Следствия: при недоступности сервиса или отсутствии подходящего профиля бот показывает исходную ошибку после одной попытки. TikTok и фото-публикации Pinterest/Instagram повторяют только чтение метаданных. X повторяет только извлечение фото, если видео уже завершилось. Старые `cookie_refresh_requests`, таймеры и Firefox-скрипты больше не используются; существующая таблица в развёрнутой базе остаётся неиспользуемой. Ручной резерв: skill `chrome-cookie-session` с атомарной установкой jar.
