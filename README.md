# Максут

Telegram-бот на Rust для скачивания доступных медиа по ссылкам YouTube, Pinterest, X/Twitter и Instagram (также TikTok). Для видео и аудио используется `yt-dlp[default,curl-cffi]` с Node.js и ffmpeg/ffprobe; фото X извлекаются отдельным Python helper из ответа Twitter в `yt-dlp`, фото Pinterest и Instagram — из метаданных `yt-dlp`. Доступность форматов зависит от публикации и сайта; закрытые, платные, удалённые или геоограниченные материалы могут быть недоступны даже с cookies.

## Запуск на ноутбуке

Нужны Docker и Compose plugin на ноутбуке с выходом в интернет. Бот уже развёрнут на `eden-notebook`; эти команды нужны для первоначальной установки новой копии или повторного развёртывания. На **ноутбуке**, из корня копии проекта перейдите в `Rust/maksut` и создайте локальный файл настроек:

```sh
cd Rust/maksut
cp .env.example .env
chmod 600 .env
```

В `.env` замените `BOT_TOKEN` на токен бота от BotFather, `OWNER_ID` — на свой числовой Telegram ID. Не оставляйте значения из шаблона. `DATABASE_URL=sqlite:///data/maksut.db`, `DOWNLOAD_DIR=/tmp/maksut`, `YTDLP_BIN=yt-dlp`, `PYTHON_BIN=/opt/yt-dlp/bin/python` и `TWITTER_HELPER=/opt/maksut/twitter_images.py` уже настроены в контейнере. База переживает пересоздание контейнера в именованном Docker volume; скачанные временные файлы — нет. Настройте SSH-ключ сервиса cookies, описанный ниже, **до** запуска бота. После этого из того же каталога:

```sh
docker compose -f compose.yaml up --build -d
docker compose -f compose.yaml logs -f maksut
```

Бот работает через исходящие соединения, без `host network`, опубликованных портов и внешней БД. Cookies обслуживает внутренний sidecar `cookie-refresh`; его порт не публикуется на хосте. Не запускайте этот Compose на рабочем ПК, если развёртывание планируется только на ноутбуке.

Для локальной разработки на Nix есть `shell.nix`: `nix-shell --run 'cargo test'` даёт Rust, Python, ffmpeg, yt-dlp и SQLite без ручной установки.

## Использование

В личном чате бот обрабатывает ссылки только от владельца (`OWNER_ID`). В группе обработка выключена по умолчанию; после включения ссылки принимаются от любого человека, но загрузки ограничены лимитом на отправителя. Остальные действия остаются owner-only: управление, стикеры и администрирование бота. Сообщения без отправителя и от других ботов игнорируются. Команды `/maksut` выполняет только владелец.

На отдельные слова (в любом регистре) бот отвечает стикером из пака «я устал это искать» и не пишет текст; триггеры работают только у владельца: `да` — «Пизда», `нет` — «Пидора ответ», `ну` — «Баранки гну», `300` или `триста` (в том числе `300$`, `300 баксов`) — «Отсоси у тракториста», `молодец`/`молодцом`/`молодцы` — «Молодцы, сосут концы», `груст*`, `депрес*`, `депрешн*`, `печал*`, `тоска`/`тосклив*`, `хандра`, `расстро*`, `подавлен*`, `поник*`, `тлен`, `паршив*`, `одинок*`, а также фразы `кошки скребут`, `нет сил`, `настроение на нуле`, `валится из рук`, `хочется плакать` — «Грустно везде». Реакция работает только там, где бот уже принимает сообщения: в личном чате владельца или во включённой группе; если в сообщении есть обрабатываемая ссылка, оно идёт обычным путём загрузки.

### Свободное общение

Если в `.env` задан `LLM_API_KEY`, бот отвечает на вопросы через `https://llm.labile.cc/v1` моделью `deepseek-v4.1-flash` (переопределяется `LLM_BASE_URL` и `LLM_MODEL`). Без ключа режим выключен и бот работает как раньше.

Характер собран по сообщениям владельца: строчные буквы, одно-два коротких предложения, без точки в конце, сухой сарказм, подколы собеседника, техносленг, редкий мат, без эмодзи и ассистентских оборотов. Lowercase, удаление точки в конце, замена длинного тире на дефис и обрезка до 280 символов принудительные, URL сохраняют регистр. `docs/communication-guide.md` вкомпилирован целиком (через `include_str!`, файл читается при сборке, не в рантайме) и добавляется в системный промпт каждого чата, где отвечает бот; правила бота идут после него и приоритетнее. В группе — только когда к нему обратились: упоминание `@имя_бота`, реплай на его сообщение или слово `максут` или `maksut`; имя вырезается из вопроса. Группа должна быть включена через `/maksut on`.

Бот помнит чат целиком: каждое сообщение пишется в SQLite с Telegram id автора, а фоновая задача раз в 10 минут сжимает старую часть в summary. В контекст идут summary и последние 40 сообщений, поэтому он знает, о чём говорили, без роста промпта. Владелец может получить стикер из 15 последних добавленных паков на его аккаунте: при старте бот читает `sticker_sets.txt` и семантический индекс `sticker_descriptions.json`, собранный `tools/build_sticker_index.py` через Telegram MCP и vision-модель. `find_stickers` ищет по описанию, настроению, персонажу или эмодзи, `send_sticker` отправляет выбранный; классические триггеры ниже работают как раньше. Бот может отправить стикер сам, без просьбы, и ответить только стикером, если текста не нужно; один стикер за ответ, без спама; сам никого не тегает и не вставляет `@упоминания`; в группах ответы уходят без реплая, чтобы не пинговать.

Семантический индекс стикеров пересобирается на хосте, где запущен Telegram MCP: `STICKER_NEWEST=15 uv run --with mcp --with httpx python tools/build_sticker_index.py`. Скрипт сам обновляет `sticker_sets.txt` (15 последних паков), скачивает листы стикеров через MCP, описывает их vision-моделью и сохраняет прогресс в `sticker_descriptions.json`; бот читает готовый индекс при старте. MCP из контейнера бота не доступен и для работы не нужен.

Бот видит вложения: фото, статичные стикеры, превью анимированных стикеров, видео и GIF, картинки-документы. Если ответить на фото или стикер и обратиться к боту, он смотрит вложение из сообщения, на которое ответили. Видео разбирается по превью, звук не слушает. Лимит вложения — 8 МиБ.

Память общая на чат: таблица `chat_messages` хранит все сообщения с `author_id`, `flags` и `compacted_at`, а `chat_summaries` - сжатый фон. Сырые сообщения не удаляются: сжатые помечаются и перестают попадать в контекст. Инъекции, секреты и мусор остаются в журнале для аудита, но не попадают в summary. В группах контекст общий, с атрибуцией по id. Попытка промпт-инъекции от не-владельца во включённой группе включает игнор на 24 часа: бот не отвечает этому `user_id` в любой группе и не кладёт его сообщения в контекст и summary; это внутреннее состояние бота, а не Telegram mute. Владелец не мьютится, повторная попытка срок не продлевает.

У модели девять инструментов: `web_search`, `research` и `read_url` для поиска и чтения публичных страниц, `propose_feature` и read-only `feature_status` доступны всем участникам; `feature_confirmation`, owner-only read-only `inspect_code`, `find_stickers` и `send_sticker` - только владельцу. `feature_status` отдаёт владельцу всю очередь, остальным только их заявки. Список, схемы и видимость задаются реестром `src/tool_registry.rs`: новый инструмент с `ToolVisibility::All` автоматически попадает в запрос к модели у всех, без отдельного списка имён. Поиск по умолчанию идёт через keyless Firecrawl (`api.firecrawl.dev/v1/search`), как в omp; `SEARCH_PROVIDER=tavily` с `TAVILY_API_KEY` или `SEARCH_PROVIDER=ddg` переключают провайдера. Нет доступа к командной строке, файлам, базе данных, чужим чатам и произвольным URL; широкий MCP не подключён. Если модель просят запустить скрипт или выполнить команду, она должна отказаться. Поиск идёт только на фиксированный хост, без переходов по редиректам; `web_search` отдаёт до пяти результатов и обрезает выдачу до 2500 символов.

### Ресерч

`research` - отдельный инструмент для обзоров и сравнений: модель выбирает его по смыслу, когда нужны несколько источников, а не один свежий факт. Она передаёт вопрос и 2-4 разных запроса; бот выполняет их параллельно, дедуплицирует URL по каноническому ключу и ранжирует: сначала источники, найденные большим числом запросов, затем по лучшей позиции у провайдера, затем по URL. На запрос берётся до 4 результатов, всего до 8 уникальных источников.

Модель получает досье с пронумерованными источниками: заголовок, URL, домен, номера запросов и фрагмент. Досье ограничено 5000 символов: при переполнении сначала режутся фрагменты, затем источники с конца. Заголовки и фрагменты очищаются от HTML, сущностей, управляющих и bidi-символов, `@`-упоминаний и URL-схем; скобки `[n]` заменяются на `(n)`, чтобы источник не подделывал цитаты. Источники - данные, не инструкции; после успешного `research` из запроса убираются инструменты с побочными эффектами, кроме случая, когда пользователь явно попросил стикер или фичу.

Финальный ответ в режиме `research` - до 6000 символов (жёсткий потолок, а не гарантия: генерация ограничена 1500 токенами): 2-5 абзацев или короткие пункты, цитаты `[n]`, строчные буквы вне URL, абзацы сохраняются. Бот сам добавляет блок `источники:` с проверенными URL из досье; невалидные номера удаляются, а если цитат нет - подставляются первые до трёх источников. Длинный ответ делится на несколько сообщений по 3900 символов. Стикер в режиме `research` автоматически не отправляется.

Лимиты: один `research` за ответ, не более 6 поисковых вызовов на ответ (`research` тратит до 4, `web_search` - по одному), общий таймаут `research` 15 секунд при HTTP-таймауте 10 секунд на запрос, персональный кулдаун 20 секунд. Если часть запросов упала, ответ строится по остальным, а в досье есть список ошибок; если упали все - `поиск недоступен`. `read_url` читает одну публичную http(s)-страницу из текущего сообщения: только домены с публичным IPv4, без localhost/приватных адресов, логина, нестандартных портов и внутренних схем; модель не может подставить произвольный URL или приклеить к нему контекст чата. Ответ ограничен 2 МиБ и 24 тысячами символов текста, весь запрос вместе с редиректами - 20 секунд; HTML сложнее 20 тысяч элементов или 128 уровней вложенности отклоняется. `research` по-прежнему работает по сниппетам и не тянет полные страницы.

Ограничения: не чаще одного ответа в 3 секунды на пользователя, до четырёх одновременных запросов к модели, до 300 токенов обычного ответа и до 1500 токенов после успешного `research`, тайм-аут 40 секунд. Telegram-обновления обрабатываются конкурентно: медленная загрузка в одном чате не сериализует остальные сообщения. При ошибке модели в группе бот молчит, в личном чате пишет короткое сообщение. Ответы отправляются тихо; в личном чате реплаем на вопрос, в группе без реплая. Длинные ответы делятся на несколько сообщений.

Отправьте боту ссылку в личный чат. Видео и аудио YouTube, Pinterest, X/Twitter, Instagram и TikTok обрабатываются, если `yt-dlp` может их извлечь. Видео WebM/MKV/MOV/AVI/M4V/3GP с видеопотоком перекодируются в MP4 (H.264/AAC) и отправляются как воспроизводимое видео, не как документ; если конвертация или отправка видео не удалась, исходная ссылка остаётся. WebM без видеопотока может отправляться документом. Подпись каждого отправленного фото, видео, аудио и документа начинается с заголовка публикации, затем пустой строки и описания, если оба поля есть (если заголовок совпадает с описанием, он печатается один раз; служебные заголовки вида `Video by …`, `Photo by …` и `<источник> video #<id>` пропускаются), затем на отдельных строках идут «От имя» в стиле кода (HTML `<code>`, только экранированный first_name отправителя, без username и фамилии, без ссылки на профиль и без упоминания) и кликабельная «Ссылка» (принятая исходная ссылка). Если исходного описания нет, пустой первой строки нет; длинный текст сокращается до лимита подписи Telegram, сохраняя имя и ссылку. Только после успешной отправки всех файлов бот удаляет исходное сообщение со ссылкой, и только если в нём не было ничего, кроме ссылки: собственный текст или вложенное медиа отправителя сохраняют сообщение, а в подпись попадает только текст самой публикации; при частичной доставке, пропущенных файлах или ошибке загрузки сообщение тоже остаётся. Фото из публикаций X/Twitter (включая цитируемую публикацию; URL вида `/status/<id>` и `/status/<id>/photo/<номер>`) извлекаются отдельным helper через приватный TwitterIE API `yt-dlp`. Helper различает публикации только с фото и публикации с видео/animated_gif по тем же медиа основной и цитируемой публикации, включая unified-card. Успешная загрузка и отправка всех фото без пропусков считается полным успехом, даже если параллельный `yt-dlp` не нашёл видео; ошибка реального видео в смешанной публикации по-прежнему сохраняет исходную ссылку. Фото Pinterest (в том числе ссылки `pinterest.ca` и `pinterest.co.uk`) и Instagram — из доступных `yt-dlp` метаданных. Ответ CDN без подходящего типа изображения не отправляется как фото или документ. Для этих источников возможны публикации с несколькими файлами, но наличие фото/видео не гарантировано: фактическая доступность и формат зависят от источника и Telegram.

Для всех источников видео выбирается вместе со звуком: отдельные видео+аудио потоки либо готовый файл с аудио (`bv+ba/b[acodec!=none]/ba`); самостоятельное аудио по-прежнему поддерживается. Перед отправкой каждого MP4 и перед конвертацией остальных видеоконтейнеров `ffprobe` обязательно подтверждает аудиодорожку; при её отсутствии или ошибке проверки видео не отправляется ни роликом, ни документом, исходная ссылка остаётся. Конвертация требует аудио и сохраняет его как AAC. Проверяется наличие дорожки, не её слышимость: тишина в исходной записи не заменяется искусственным звуком. Прежний кэш `file_id`, созданный без проверки звука, не используется; новые проверенные доставки кэшируются как раньше.

После проверки размеров и подготовки файлов бот сохраняет их порядок и объединяет соседние совместимые медиа в альбомы по 2–10 элементов: фото и видео можно смешивать, аудио группируются только с аудио, документы — только с документами. Одиночный элемент отправляется отдельно. У каждого элемента остаются своё описание, экранированное имя текущего отправителя в стиле кода и кликабельная исходная ссылка; одинаковая подпись (например, у фото-публикации без текста) отправляется только с первым таким элементом альбома, чтобы не повторяться; альбомы тоже отправляются тихо ([Telegram `sendMediaGroup`](https://core.telegram.org/bots/api#sendmediagroup)).

При отказе или неопределённом результате отправки альбома бот не повторяет его по одному файлу: Telegram мог уже принять медиа, и повтор создал бы дубликаты. При частичной доставке исходная ссылка остаётся. Прежняя резервная отправка одиночного загружаемого фото/аудио документом сохраняется только при однозначном отказе Telegram, не при сетевой ошибке или тайм-ауте; для альбомов такой подмены нет.

HTTP-запрос к Telegram ограничен 180 секундами суммарно на отправку тела и ожидание ответа; установление соединения — 5 секундами. Это отдельный лимит от 180 секунд загрузки с сайта и подготовки медиа. Тайм-аут по-прежнему означает неподтверждённую доставку: автоматического повтора отправки нет.

Все исходящие сообщения бота отправляются тихо (`disable_notification=true`): фото, видео, аудио, документы, резервная отправка фото/аудио документом, ответы на команды, ошибки и предупреждения. Это отключает звук, но уведомления могут по-прежнему отображаться. Цвет текста в стиле кода зависит от клиента Telegram и его темы; бот не задаёт серый цвет.

Короткие ссылки `pin.it`, `vm.tiktok.com` и `vt.tiktok.com` бот разрешает до канонического адреса публикации перед загрузкой: у `yt-dlp` нет экстракторов для этих хостов, а generic-экстрактор отключён. Для TikTok бот передаёт Firefox User-Agent, поскольку с этой сети сайт отдаёт заглушку «Site Maintenance» на Chrome-подобный User-Agent. При равном разрешении для TikTok предпочитается H.264: HEVC-варианты иногда не содержат аудиодорожки, хотя `yt-dlp` сообщает AAC.

Фото-публикации TikTok (`/@автор/photo/<id>`, в том числе через короткую ссылку) обрабатываются отдельно от `yt-dlp`: бот читает метаданные страницы TikTok и скачивает до 35 изображений по проверенным HTTPS-адресам CDN, отправляя их несколькими альбомами; если первый адрес изображения недоступен, пробует следующий из той же публикации. TikTok-cookies из закрытого файла передаются только запросу страницы `www.tiktok.com`, не CDN. Видео TikTok по-прежнему загружает `yt-dlp`; доступность зависит от публикации и сети.

Отказы источников не всегда связаны с форматом: TikTok может вернуть страницу без адреса видео (`10204 / content_classification,status_reviewing`), которую закреплённый `yt-dlp` описывает как IP-блокировку; бот сообщает об ограничении доступа, не утверждая точную причину блокировки. Instagram может явно ограничить аудиторию публикации; этот отказ также получает отдельное объяснение. Обновление загрузчика или cookies не гарантирует снятия ограничений сайта.

Для отдельного ролика YouTube (не плейлиста и не ссылки с `list=`) бот сначала запрашивает метаданные в пределах общего времени загрузки. Если известны точные размеры потоков и вместе с запасом на упаковку в MP4 они помещаются в `MAX_MEDIA_BYTES`, он выбирает лучшее доступное разрешение/частоту кадров H.264 + AAC (либо готовый MP4 с этими кодеками) и объединяет потоки без перекодирования. Это добавляет запрос метаданных, но экономит время и CPU на конвертации; максимальное разрешение не гарантировано: для `https://youtu.be/1H9izmMrCvQ` при лимите 45 МиБ выбирается 720p (136+140), потому что 1080p (137+140) не помещается. Если подходящих форматов/достоверных размеров нет, запрос метаданных не удался или трансляция ещё идёт, остаётся прежняя загрузка лучшего формата `yt-dlp` и при необходимости конвертация через ffmpeg. Если выбранный MP4 не скачался и готовых файлов нет, бот однократно пробует прежний способ в оставшееся время; после тайм-аута или достижения лимита попытка не повторяется. Плейлисты и другие сайты обрабатываются по-прежнему.

Для перекодирования выбирается только движущийся видеопоток, не обложка; файл только с обложкой не отправляется как видео или документ. Перед конвертацией ограничиваются входные размеры: каждая сторона до 3840 пикселей, не более 8 294 400 пикселей в кадре. Видео с большим разрешением отклоняется, исходная ссылка остаётся. Выходной MP4 ограничен 1920 пикселями по каждой стороне без увеличения небольших роликов (включая вертикальный формат 1080×1920), нечётные размеры дополняются до чётных для H.264/yuv420p.

YouTube-ролики длиннее 30 минут, live-трансляции и upcoming-стримы не скачиваются: `yt-dlp` получает `--match-filter "!is_live & duration < 1800"` и завершает такой ролик до открытия медиапотока. Остальные источники ограничены размером файла, таймаутом загрузки и лимитом файлов. В образе закреплена версия `yt-dlp[default,curl-cffi]==2026.7.4`; helper X зависит от приватного API TwitterIE этой версии. При изменениях X API или ответов сайта потребуется обновить `yt-dlp` и согласованно изменить helper, затем пересобрать образ на ноутбуке. Cookies, доступные только владельцу аккаунта, могут помочь с авторизацией, но не гарантируют загрузку и не отменяют ограничения источника. Для видео YouTube с cookies бот передаёт `--extractor-args youtube:player_client=default,web_embedded`: это обход несовместимости авторизованного YouTube с закреплённым `yt-dlp` ([upstream issue #17389](https://github.com/yt-dlp/yt-dlp/issues/17389)); без cookies и для других сайтов флаг не используется.

В группах обработка ссылок по умолчанию выключена; только владелец (`OWNER_ID`) может управлять ею командами `/maksut on` и `/maksut off`, `/maksut status` показывает состояние. Для получения обычных сообщений со ссылками отключите Privacy Mode для бота через BotFather: `/setprivacy` → выберите бота → `Disable`, затем удалите бота из группы и добавьте снова, чтобы настройка вступила в силу. Это ручная настройка владельца, бот её не меняет. Дайте боту право отправлять медиа/файлы и назначьте его администратором группы с правом удаления сообщений (`can_delete_messages`): без него медиа остаются в группе, но исходную ссылку бот удалить не сможет и сообщит об этом. Администрирование — только командами Telegram.

Включённая группа разрешает загрузку и конвертацию любому человеку; каждый отправитель ограничен отдельным лимитом, а выключить группу командой `/maksut off` может только владелец. После успешной отправки файлов бот не посылает отдельное сообщение со счётчиком или статусом; при ошибке либо частичной доставке сообщает причину и сохраняет исходную ссылку (при невозможности удалить ссылку сообщает о требуемом праве).

Обычные сообщения без поддерживаемой ссылки, не адресованные боту, не обращаются к настройкам группы и остаются без ответа даже при ошибке базы данных. После `/maksut off` ссылки участников, ожидающие свободного слота загрузки, отбрасываются; уже начавшаяся загрузка не отменяется.

Обработчики асинхронные (Tokio/teloxide); одновременно выполняются не более двух задач загрузки, остальные ждут свободный слот. Конвертация запускается отдельным процессом ffmpeg и не блокирует цикл обработки сообщений.

По умолчанию лимит одного файла — 45 МиБ (47 185 920 байт); его можно задать в `.env` через `MAX_MEDIA_BYTES` от 1 до 50 000 000 байт. Абсолютный предел отправки — 50 000 000 байт; за одну ссылку обрабатывается не более 10 файлов, для фото-публикаций TikTok — до 35. Для пакетной загрузки и перекодирования нужно свободное место для временных файлов (включая входной и выходной файл); время загрузки и конвертации ограничено. Файлы, превышающие предел до или после конвертации, нельзя отправить ботом в этом режиме. Слишком большие, недоступные или требующие дополнительных прав публикации могут не загрузиться.

Завершённые файлы неподдерживаемого формата считаются пропущенными: если по ссылке скачались и поддерживаемый файл, и неподдерживаемый (например, FLV), первый отправляется, но исходная ссылка не удаляется.

### Самоулучшение

Владелец в личном чате с ботом может попросить изменить сам бота:

```text
/improve добавь в README раздел про самоулучшение
/improve status <id>
/improve off
```

Владелец может принимать решения кнопками или явным текстом в личке: `одобри #id`, `отклони #id`, `отмени #id`, `подними #id`, `опусти #id`, `приоритет #id 1`. Те же действия доступны как `/improve approve|reject|cancel|priority <id>`. Сообщения из групп и форварды текст не одобряют. `cancel` убирает только ожидающую задачу; выполняющуюся не убивает. `отмени` принимает несколько id в одном сообщении и отменяет все подходящие задачи одним ответом; ненайденные и уже выполняющиеся перечисляются отдельно и не мешают остальным. Id можно писать как в очереди: полный (`plan-…-214534`), короткий (`214534`) или его уникальный числовой префикс/суффикс (`34`); неоднозначный фрагмент бот переспросит, а не соврёт, что задачи нет. Приоритет хранится в задаче и сортирует очередь.

Перед предложением изменений в коде owner-модель может вызвать read-only `inspect_code`: поиск и чтение по снимку `src/`, `tools/`, `docs/`, `Cargo.toml`, `README.md`. Секреты, `self-improve`, cookies и `target` исключены; shell и запись недоступны.

Можно без команды: владелец пишет в личку; в группе и владелец, и остальные обращаются к боту (`@бот`, reply на сообщение бота или имя `максут`/`maksut`), а группа должна быть включена. Фраза может быть любой, вроде «давай ебанем фичу с ...». Бот не матчит ключевые слова: модель по смыслу вызывает инструмент `propose_feature`, который кладёт в `./self-improve/inbox` задачу со стадией плана. Вопросы про статус, план, задержку и прошлое решение модель закрывает read-only инструментом `feature_status`, вопросы «что ждёт подтверждения» и просьбы вида «делаем»/«отмена» — read-only `feature_confirmation`, который только возвращает очередь и кнопки. Инструменты не меняют состояние; решения принимаются кнопкой или явной командой владельца. `propose_feature` с `refines=<id>` создаёт дочерний план, не отклоняя старый. Оркестратор сразу создаёт GitHub issue со спекой и ревью, бот присылает владельцу короткую ссылку и кнопки «Делаем» / «В помойку», а для готового деплоя — «Деплой» / «В помойку»; одобрять или удалять может только владелец. Host-orchestrator `tools/self_improve_orchestrator.py` делает снапшот рабочего дерева, запускает read-only planner и reviewer в одноразовом контейнере без home, `.env`, `.secrets`, SSH-к…

Orchestrator запускается как user unit:

```sh
cp packaging/maksut-self-improve.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now maksut-self-improve.service
journalctl --user -u maksut-self-improve.service -f
```

Issue создаётся через `gh`; репозиторий задаётся `SELF_IMPROVE_GITHUB_REPO` (по умолчанию `labi-le/maxwell`). После успешного деплоя orchestrator закрывает issue с комментарием «Задеплоено.»; при отклонении плана — с комментарием об отклонении. Планировщик по умолчанию использует `SELF_IMPROVE_MODEL`; его можно переопределить через `SELF_IMPROVE_PLAN_MODEL` и `SELF_IMPROVE_PLAN_THINKING`.

Запуск агента вынесен в `tools/omp_worker.py`: JSON на stdin, JSON на stdout. Оркестратор оставляет у себя очередь, approval, base snapshot, тесты и deploy, а worker только запускает OMP в одноразовом контейнере. Ключ модели не передаётся в job JSON или argv: worker монтирует подготовленный `profile` read-only. Контракт описан в `docs/adr/017-omp-worker-contract.md`; roboomp не является зависимостью.

`self-improve/` исключён из Git и Docker build context, чтобы задачи и временные profile с ключом не попадали в образ. Каталог должен существовать на хосте до `docker compose up`; бот монтирует его в `/var/lib/maksut/self-improve`.

### Повторные ссылки: кэш на 24 часа

После полной подтверждённой доставки бот запоминает Telegram `file_id` и при повторе **той же принятой нормализованной ссылки, включая все query-параметры, в том же чате и с тем же токеном бота** отправляет медиа по этим идентификаторам, без повторной загрузки с сайта и без загрузки байтов в Telegram ([правила Telegram для `file_id`](https://core.telegram.org/bots/api#sending-files)). Другой чат, отличающийся query или смена токена дают отдельный ключ. Кэш не обходит авторизацию и `/maksut off`: проверки доступа и повторная проверка состояния группы после ожидания слота действуют и для повторных ссылок. Порядок, фактически доставленные типы и группировка сохраняются; подписи заново получают имя текущего отправителя и текущую исходную ссылку.

Срок — **24 часа от сохранения результата свежей загрузки**, попадание в кэш его не продлевает. После истечения срока бот снова обращается к источнику; повреждённая запись тоже считается промахом. В общей SQLite-базе сохраняются не более 200 новейших записей публикаций суммарно для всех чатов, поэтому запись может быть вытеснена раньше. Кэш переживает перезапуск с сохранённой базой. Просроченные записи очищаются лениво при обращениях, а не гарантированно в секунду истечения срока.

Запись создаётся только для полностью полученных и доставленных медиа без пропусков, если Telegram вернул пригодные `file_id` для всех элементов. Частичная загрузка/доставка, пропущенные файлы или отсутствие идентификатора не заполняют кэш; отсутствие `file_id` само по себе не отменяет успешную доставку. Неудачное удаление исходного сообщения не мешает сохранить полностью доставленные медиа. Если Telegram однозначно отклонил устаревший `file_id` и ещё ни один элемент не доставлен, бот сбрасывает запись и один раз пробует свежую загрузку. После частичной доставки, при 429, сетевой ошибке, тайм-ауте или неоднозначном ответе он не начинает загрузку/отправку заново и сохраняет исходную ссылку.

Таблица `media_cache` хранит чат, время, хеш ключа и упорядоченные фактические типы/`file_id`/исходные описания до HTML-экранирования (описание ограничено 1024 единицами UTF-16, готовая подпись с именем и ссылкой — прежним лимитом 1024). Байты медиа и прежние подписи с именем отправителя не сохраняются; полный URL с query и токен участвуют в SHA-256 ключе, но не записываются открытым текстом как поля ключа. В течение срока кэша бот не проверяет источник заново: изменённая или удалённая публикация может по-прежнему отправляться со старым описанием. Ограничение доверенными группами и предупреждение о доступе через cookies владельца остаются в силе; сама база с идентификаторами и описаниями тоже не предназначена для публикации.

### Причины ошибок

Бот сообщает только причину, подтверждённую безопасной категорией ошибки:

- У источника различаются отказ HTTP 403, отсутствие HTTP 404, закрытая/недоступная публикация, необходимость авторизации или истёкшие cookies, ограничение частоты HTTP 429, временный сбой HTTP 5xx, тайм-аут, превышение размера отдельного файла, исчерпание общего лимита временных данных, неподдерживаемая ссылка/экстрактор и отсутствие метаданных или медиа. Обновление cookies не запускается от любой 403 и не гарантирует её устранения.
- При доставке различаются ограничение Telegram 429 (с указанным временем ожидания, если оно известно), слишком большой файл, отсутствие прав/блокировка/исключение бота, непригодный `file_id`, сетевой сбой/тайм-аут и некорректный ответ/ошибка ввода-вывода.

Если причину определить нельзя, бот честно сообщает, что она неизвестна, а не приписывает её ссылке или cookies. После существующего повтора с обновлёнными cookies либо другим форматом пользователю показывается последняя существенная причина из трассы; исходная ошибка авторизации остаётся в родительской записи журнала или в упорядоченной трассе, если видео сообщило более конкретную причину. Сырые stderr и ответы API, диагностические URL, токены и cookies не пересылаются в чат и не записываются в журнал — используются безопасные категории. Это не меняет обычную кликабельную «Ссылку» в подписи медиа, команды, лимиты загрузки или правила обновления cookies. Решение: [ADR 006](docs/adr/006-albums-errors-cache.md).

## Cookies Chrome с ноутбука или ПК

Источник cookies: авторизованный профиль Chrome `~/.config/google-chrome/Default/Cookies` на `notebook` или `pc`. Firefox и скрипты `sync_firefox_cookies.py` больше не используются. Chrome хранит ключ расшифровки в keyring того хоста, поэтому экспорт запускается по SSH на самом ноутбуке или ПК, а не в контейнере бота. `tools/export_chrome_cookies.py` расшифровывает `v10`/`v11`, оставляет домены площадок, пишет Netscape jar в stdout и безопасную сводку в stderr.

Сервис `cookie-refresh` собирается из `cookie_refresh/Dockerfile`, по очереди опрашивает `pc` и `notebook`, выбирает самый свежий профиль Chrome с cookie нужного источника и атомарно записывает `cookies.txt` с правами `0600`. Бот получает тот же каталог через `${MAKSUT_COOKIES_DIR:-/home/eden/.local/share/maksut/cookies}` только для чтения, а сервис монтирует его для записи. Перезапуск бота после замены файла не нужен.

Перед первым запуском создайте отдельный SSH-ключ сервиса и добавьте его на оба хоста:

```sh
install -d -m 700 .secrets/cookie-refresh
ssh-keygen -t ed25519 -N '' -f .secrets/cookie-refresh/id_ed25519
ssh-copy-id -i .secrets/cookie-refresh/id_ed25519.pub labile@pc
ssh-copy-id -i .secrets/cookie-refresh/id_ed25519.pub labile@notebook
ssh-keyscan -H pc notebook > .secrets/cookie-refresh/known_hosts
chmod 600 .secrets/cookie-refresh/id_ed25519 .secrets/cookie-refresh/known_hosts
```

Сверьте отпечатки из `ssh-keyscan` с известными отпечатками хостов: `known_hosts` доверяет первому сканированию. Ключ можно ограничить в `~/.ssh/authorized_keys` на каждом хосте, добавив перед строкой ключа `command="python3 -",restrict`. Тогда сервис сможет только запускать экспортёр через stdin, без интерактивного shell; после изменения проверьте refresh вручную.

Каталог `.secrets/` исключён из Git и Docker build context. В Compose уже заданы `COOKIE_SSH_TARGETS=labile@pc,labile@notebook`, `COOKIE_HOST_PC=192.168.1.3`, `COOKIE_HOST_NOTEBOOK=192.168.1.155` и внутренний адрес `COOKIE_REFRESH_URL=http://cookie-refresh:8080`. Порт сервиса не публикуется на хосте. Если адрес или пользователь SSH отличаются, переопределите эти переменные в `.env`.

Сервис отвечает на `GET /healthz` и `POST /refresh` с телом `{"source":"youtube"}`. Поддерживаются `youtube`, `tiktok`, `instagram`, `twitter`, `pinterest` и `generic`. Успешный ответ означает, что jar уже установлен; при отсутствии подходящего профиля сервис возвращает `503` и не трогает текущий файл.

### Обновление по ошибке авторизации

Бот обращается к `cookie-refresh` только при явной ошибке авторизации, истёкших cookies или недоступном cookie jar. Для видео и метаданных он не повторяет загрузку, если уже есть завершённые файлы, которые нужно отправить; для X повторяется только helper фото, а готовое видео не перезаписывается. После успешной замены jar бот один раз повторяет нужную операцию. Обычная HTTP 403, закрытая публикация, удалённое медиа или отсутствие метаданных обновление не запускают. Если сервис недоступен, не нашёл подходящий профиль или новый jar всё равно не проходит авторизацию, бот показывает исходную ошибку и не зацикливается.

TikTok и фото-публикации Pinterest/Instagram обновляют cookies до повторного чтения метаданных. Для X повторяется только извлечение фото, уже завершённое видео повторно не скачивается. Предупреждение `cookies are no longer valid` при успешной загрузке повтора не вызывает. Решение: [ADR 008](docs/adr/008-docker-cookie-refresh-service.md).

Если сервис временно недоступен, используйте skill `chrome-cookie-session` для ручного экспорта с `notebook` или `pc`. Не направляйте вывод экспортёра в живой `cookies/cookies.txt`: сначала сохраните его во временный файл, проверьте и установите через `install -m 600`. Старые пользовательские таймеры `maksut-cookie-sync.timer` и `maksut-cookie-refresh.timer` из репозитория удалены; если они остались на ПК, отключите их:

```sh
systemctl --user disable --now maksut-cookie-sync.timer maksut-cookie-refresh.timer
```

Токен и cookies нельзя коммитить, включать в Docker build context, выкладывать в логи или чат или передавать в Telegram как файл. `.env` хранится только на ноутбуке с закрытыми правами; в Git добавляйте лишь `.env.example` с вымышленными значениями. Cookies могут давать доступ к аккаунту: храните их отдельно, регулярно обновляйте и отзывайте при утечке.

## Обслуживание

```sh
docker compose logs -f maksut  # посмотреть ошибки
docker compose down             # остановить, сохранив volume с базой
docker compose up --build -d    # обновить после получения нового кода
```

Не используйте `docker compose down -v`, если нужно сохранить настройки в базе. Для смены токена, `OWNER_ID` или каталога cookies отредактируйте `.env` на ноутбуке и пересоздайте сервис `docker compose up -d --force-recreate`; обычное обновление файла cookies внутри каталога этого не требует. `BOT_TOKEN` и `OWNER_ID` контейнер получает из `.env` через `env_file`, поэтому экспортированные в оболочке значения этих переменных файл не переопределяют.

Откат альбомов, новых причин ошибок и кэша: восстановить сохранённые исходники из `target/maksut-rollbacks/albums-errors-cache-2026-10-08` и вернуть прежний образ бота (либо собрать его из этих исходников). На ноутбук нужно передать восстановленную версию, не удаляя volume SQLite, `.env` или cookies. Таблицу `media_cache` безопасно оставить: прежний образ её игнорирует. Настройки BotFather и cookies при таком откате не меняются; старые таймеры cookies текущая версия не использует, и при откате на образ до ADR 008 их нужно вернуть отдельно.

### Диагностика неудачных загрузок

Причины ошибок загрузки, пропущенных файлов и недоставленных медиа сохраняются в таблице `download_failures` той же SQLite-базы в Docker volume (не более 200 последних записей). Для каждого сбоя в `download_failure_events` сохраняется упорядоченная трасса: этапы первой попытки, запроса/подтверждения обновления cookies, повтора и доставки; безопасная категория и код завершения каждого неудачного процесса. Родительская запись сохраняет время UTC, хост и путь ссылки без query, исходную причину (в том числе исходную ошибку авторизации после неудачного повтора); актуальная причина повтора остаётся в событиях и используется для ответа пользователю. Дочерние события удаляются вместе с родительской записью при ограничении журнала. Сырые stderr и ответы API, полные диагностические URL, cookies, токен бота и параметры ссылок не сохраняются. Неизвестный текст ошибки `yt-dlp` остаётся общей категорией; трасса показывает, на каком этапе и с каким кодом она возникла. Последние 30 ошибок вместе с событиями (на ноутбуке из каталога проекта):

```sh
docker compose -f compose.yaml exec -T maksut python3 -c 'import sqlite3; db=sqlite3.connect("file:/data/maksut.db?mode=ro", uri=True); print(*db.execute("SELECT f.rowid, f.created_at, f.url_host, f.url_path, e.event_index, e.stage, e.detail, e.exit_code FROM (SELECT rowid, * FROM download_failures ORDER BY rowid DESC LIMIT 30) AS f JOIN download_failure_events AS e ON e.failure_rowid = f.rowid ORDER BY f.rowid DESC, e.event_index"), sep="\n")'
```

В чат пересылайте только строки этой выборки, не `.env`, `cookies.txt` и не полную базу. Записи до появления `download_failure_events` не имеют событий повтора.
